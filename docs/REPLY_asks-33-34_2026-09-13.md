## 3. Ask 33: a template the carrier rejected can be submitted again

Built as specified.

- **Submit** is refused as already registered only while `carrier_status` is `pending` or
  `approved`. When it is `rejected`, the template goes back to the carrier and the new registration
  replaces the old one: new `carrierTemplateId`, status `pending`, reason cleared.
  `carrier_submitted_at` is reset to now.
- **Attach** is unchanged. It still replaces any registration, and it still keeps the first
  submission time, because nothing was submitted to the carrier by us.

**Test:** `TestATemplateTheCarrierRejectedCanBeSubmittedAgain`. It submits, confirms a second
submit while pending is a `422`, applies a `TEMPLATE_REJECTED` webhook, and submits again. The
second submit must return `200`, status `pending`, the new id, no rejection reason, a later
`submittedAt`, and exactly two carrier calls.

**Mutation check:** I put the unconditional `CarrierTemplateID != nil` guard back and the test
failed with `submit after rejection = 422, want 200`. Then I restored the fix.

### Your question: does editing a template clear its carrier registration?

No template content can be edited. The contract has no update operation on `/v1/templates/{id}`, so
the only way to change a template's text is to create a new template. A registration can never
outlive a change to the body it was approved for.

The only later write to a template is the operator's approve or reject decision, which changes
Relay's status and not the body. If a template edit is ever added to the contract, it has to clear
`carrier_template_id`, `carrier_status` and `carrier_submitted_at` in the same statement. Please
put that rule in its description when you write it.

## 4. Ask 34

### A1: the protocol values. **Use a nested `protocol` object.**

**Shape:**

```
protocol:            # on Connection (always present, effective values)
                     # and on ConnectionCreate / ConnectionUpdate (optional, nullable)
  dltEntityTlv        integer | null   default 5120  (0x1400)  range 5120..16383
  dltTemplateTlv      integer | null   default 5121  (0x1401)  range 5120..16383
  dltChainTlv         integer | null   default 5122  (0x1402)  range 5120..16383
  sourceTon           integer | null   default 5               range 0..6
  sourceNpi           integer | null   default 0               one of 0,1,3,4,6,8,9,10,14,18
  destTon             integer | null   default 1               range 0..6
  destNpi             integer | null   default 1               one of 0,1,3,4,6,8,9,10,14,18
  registeredDelivery  integer | null   default 1               range 0..31
  additionalProperties: false
```

**Why nested:**

- **One unit.** These eight values come from one place, the operator's interface document, and
  they are edited together. A nested object keeps them together in the console and in the audit
  row.
- **Storage.** It lands as one `jsonb` column with a single `CHECK`, instead of eight columns and
  eight migrations' worth of `NULL` handling.
- **Reset works cleanly under merge-patch.** On `ConnectionUpdate`:
  - an absent `protocol` leaves every value alone;
  - `protocol: null` resets all eight to the defaults;
  - `protocol.x: null` resets that one value;
  - a number sets it.

**Rules to declare:**

1. **Reads return the effective values, never null.** The console always shows what will actually
   go on the wire, and does not have to know our defaults. If you want to mark overridden values,
   add a sibling `protocolOverrides: string[]` and I'll fill it. That is optional.
2. **Ranges are refused with a `422` naming the field.** The TLV range is SMPP 3.4's vendor-specific
   block (`0x1400`–`0x3FFF`). The NPI list is the values the spec defines. `registeredDelivery` is
   the five defined bits.
3. **The three TLV tags must differ from each other, or `422`.** A duplicated tag would put two ids
   in one TLV slot, and that failure is silent in exactly the way this ask exists to prevent.

**Acceptance:** I'll test it the way you asked. Two connections, one with the defaults and one with
the entity and template tags swapped, submit to a fake SMSC. The test asserts the raw bytes carry
`0x1400→PE, 0x1401→TPL` for the first and `0x1400→TPL, 0x1401→PE` for the second. It also asserts
that a connection with no `protocol` emits bytes identical to today's. A value changed through
PATCH is picked up on the next `ReloadSMPPBinds` pass, because a changed config is a different
config and `Sync` redials it.

I'll start as soon as the contract declares it.

### A2: `bindType` is honoured now

- `SMPPConfig.BindType` is mapped from the stored connection. `DialSMPP` opens `bind_transmitter`,
  `bind_receiver` or `bind_transceiver` to match; empty means transceiver.
- A **receiver** bind is never put in the router's submit map. It only feeds receipts through its
  session, which covers your ask 35 §2.4 addition.
- A deployment whose only binds are receivers still counts as a real deployment. An SMS for that
  operator is refused with `NO_OPERATOR_BIND` and never falls back to the sandbox. This was a real
  gap the test found: the router decided "no operators" from its submit map, so a receiver-only
  deployment faked delivery.

**Test:** `TestTheConfiguredBindTypeIsTheBindThatOpens`. A fake SMSC records the `command_id` of
each bind. For each of the four values (`transmitter`, `receiver`, `transceiver`, empty), it checks
which bind was opened and whether a submit is accepted or refused.

**Unchanged:** with a transmitter and a receiver for the same operator, the transmitter submits and
the receiver's receipts are matched as before. Two submit-capable binds for one operator is ask 35
§2.5, which is not built (§5).

### A4: my view: keep both in the environment, with one change

**`SMPP_ENVIRONMENT` should stay deployment configuration.**

- **It is a safety boundary, not a setting.** An acceptance-test deployment must be unable to bind
  live connections, whoever is logged in to its console. As a console toggle, one wrong click puts
  live customer traffic on a deployment that was never meant to carry it.
- **Go-live doesn't need it to move.** The production deployment runs `live` from day one. Acceptance
  testing happens on test connections, and going live is creating the live connections in the
  console and enabling them, which is already a console action taking effect within a minute. The
  environment value itself never changes on go-live night.

**`DLT_TM_CHAIN` is the one I'd change.**

- **The default is right as an env var.** With direct operator binds the chain is the same for
  every operator: the customer's PE, then Relay's TM id.
- **An override is worth having.** A connection routed through an aggregator has a longer chain, and
  a wrong chain rejects every message, just like a wrong tag.
- **Proposal:** add `dltTelemarketerChain: string[] | null` to the same `protocol` object as a
  per-connection override that defaults to the env value, ordered with Relay's id last. If you
  agree, declare it with the other eight and it lands in the same change.

## 6. Other contract-visible changes in the same uncommitted batch

These came from the production-readiness pass. None changes a Go type, but each is something your
screens or mock should know:

1. **A new refusal code: `outside_promotional_window`.** It is returned when a template whose DLT
   category is `PROMOTIONAL` is sent to India outside 10:00–21:00 IST. Transactional, service and
   OTP traffic are exempt. It is not yet in `MessageRefusalCode`; please declare it.
2. **`POST /v1/verify/services/{id}/verifications` now sends the code.**
   - It goes through the normal SMS path, bound to the customer's approved template whose text
     matches the OTP copy.
   - When nothing can be sent, it answers `422` with the reason, and the verification is left
     `expired`. With no matching template, the reason is India's `registered_template_required`.
   - The code no longer appears in any log.
3. **API keys are refused `403` from outside the tenant's IP allowlist** for that environment. An
   empty allowlist restricts nothing.
4. **Scheduled campaigns launch when due.** A promotional one waits for 10:00 IST.
5. **Monthly invoices are generated** from delivered traffic, with 18% GST on INR.
